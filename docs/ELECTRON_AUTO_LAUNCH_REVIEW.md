# Electron 自动启动适配 Review

日期：2026-11-12。

## 实现结果

桌面应用通常只需保存 `amp-desktop`、`t3code` 或程序路径。后端在每次启动时识别程序，生成实际执行命令；数据库中保存的原命令不变。编辑器移除了 Electron 模板、模板沙箱勾选项和长说明，兼容策略、沙箱策略、实际运行身份及上次启动详情收进默认折叠的“高级启动设置”。下拉框复用现有样式和交互，中英文同步更新。

自动识别使用应用实际的 PATH、HOME、静态环境赋值及有效用户执行权限，解析软链接，检查 ELF 内的 Electron 专属标记、版本及资源布局，不执行目标程序的 `--version`。支持标准 `env`、`dbus-run-session` 和纯 `exec /path/to/app "$@"` 包装脚本；普通程序、Electron Node 模式和无法可靠解析的命令保持原样。扫描有大小、时间上限和文件身份缓存，程序更新后重新检查。

确认 Electron 后按可识别能力补充缺失的 Wayland、IME 与 text-input-v3 参数。已有参数、引号和用户参数保持不变，补参置于目标程序后、用户参数及 `--` 分隔符前。重复开关按最后一个值判断；显式 X11 后端和沙箱策略冲突明确报错。

自动沙箱策略在有效 UID 为 0 时，仅对确认或明确指定为 Electron 的应用补充 `--no-sandbox`，这会关闭该应用的 Chromium 沙箱。普通用户不自动禁用沙箱；“保留沙箱”不因启动失败降级。“原样执行”完全保留命令，不应用兼容或沙箱策略。

主桌面、独立 worker、自动启动和 watchdog 复用同一适配入口。静态识别不足时，只有 10 秒内精确的 Electron 初始化失败日志，结合目标自身的 Electron 二进制特征或 AppImage 标记，才允许一次兼容修正；整个第一轮进程树必须已退出。停止请求、已记录窗口就绪、更新的启动代次和 raw 模式均阻止兼容重试。原有有上限的 watchdog 仍处理其他失败。

启动记录写入应用持久目录下权限为 0600 的 `launch-info.json`，记录原命令、实际命令、UID、识别结果、补参、启动代次和窗口就绪标记，不包含完整环境及内部诊断日志路径。控制台按需读取，管理接口为认证后的 `GET /api/apps/<id>/launch-info`。新增 SQLite 配置列可自动迁移；旧客户端更新时不传新字段则保留原策略。

## 整体审查及修正

- 识别不能仅依靠应用名、Chromium 资源或日志：联合检查二进制特征，避免普通 X11 程序以及启动器内部 Electron 错误触发错误补参。
- PATH 解析按有效用户的执行权限跳过不可执行的同名文件；透明包装器严格要求参数独立转发，避免改变外层脚本语义。
- 兼容重试由 subreaper 收集整棵第一轮进程树后执行；恢复应用的信号掩码，检查待处理的停止信号，保留既有停止宽限时间。
- 修正独立 worker 使用私有 `IVNC_HOME` 导致诊断目录偏离的问题：日志和启动记录统一按传入应用 HOME 的父目录定位，并验证新的启动代次确实刷新记录。
- 当前启动代次一旦出现窗口便记录 sticky 标记，避免曾经成功出图的应用在退出后被误判为初始化失败；不同启动代次的记录不能授权旧尝试重试。
- 首轮错误与修正后的错误以重试标记隔开，诊断取最新尝试；控制台刷新签名包含 `launch_error` 和 `window_ready`，状态值相同时错误说明仍会更新。
- 检查数据库迁移、旧 API 行为、无效策略拒绝、弹窗异步取消及跨应用状态清理；检查默认简洁布局、展开高级设置与窄屏下拉框边界。

上述问题均已处理，未发现尚未处理的阻断问题。

## 兼容边界

- 本轮没有部署或启动远程生产实例中的 amp-desktop/t3code。此前只读检查确认其 Electron 二进制特征；当前实际运行验收基于 Electron 45.3.1 测试应用，不能等同于生产应用的业务验收。
- 复杂 shell、身份切换和不透明启动脚本默认不自动改写；可按发行包规则使用直接命令，或在高级设置明确指定兼容方式。“指定为 Electron”仍要求可安全解析的命令。
- AppImage 的 FUSE/解包、Flatpak/Snap 封装、动态库、Secret Service、通知、portal 和账户配置仍由部署提供。普通用户沙箱失败不会自动禁用沙箱。
- 不增加 X11/XWayland 或按应用切换 UID。需要保留沙箱时，让 iVnc 与应用从启动时使用同一普通用户，参见 [NONROOT.md](NONROOT.md)。
